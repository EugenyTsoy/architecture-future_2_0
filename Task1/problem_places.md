| № | Проблема | Бизнес-эффект | Причина | Рекомендация|
|---:|---|---|---|---|
| 1 | Monolithic DWH с embedded business-logic | Медленная выдача отчётов, долгий time-to-market для новых отчётов, риск ошибок при изменениях | Бизнес-правила и трансформации реализованы в хранении (T-SQL, PowerBuilder), нет разделения ответственности | Отделить операционные и аналитические потоки: оставить legacy как read-only, перенести ETL/логики в data products (ELT на Lakehouse), внедрить тесты и CI для трансформаций |
| 2 | Отсутствие событийной интеграции (CDC → нет единого источника правды) | Долгая и ненадёжная синхронизация данных между доменами; сложные интеграции с новыми партнёрами | Интеграция через кастомную шину + прямые модификации DWH | Ввести потоковую шину (Kafka), CDC (Debezium) для всех источников, стандартизировать события и контракт API |
| 3 | Нет единого семантического слоя для BI | Различные интерпретации метрик между отделами, дорого и долго настраивать отчёты | Разные BI-виды подключаются к разным таблицам/представлениям | Построить semantic layer / metrics layer (общий набор определений, access control), подключить портал витрин |
| 4 | Медицинские карты хранятся централизованно в DWH и смешаны с аналитикой | Риски соответствия (GDPR/HIPAA подобные), потенциальный юр-риск и сложности с разграничением доступа | Исторически DWH содержит всё, нет чёткой классификации PII/PHI | Вынести мед.карты в изолированный клинический стор (access-controlled), исключить их из аналитической витрины; применить маскирование/андонимизацию где нужно |
| 5 | Отсутствие data governance, lineage и каталога | Долго выяснять источник данных; высокие риски ошибок в отчётах | Нет механизма регистрации датапродуктов, метаданных и owner'ов | Внедрить Data Catalog + процессы владельцев данных и SLA для датапродуктов |
| 6 | Сложные интеграции с внешними партнёрами (фарма, производитель) | Риски задержек при подключении новых бизнесов; возможны ручные операции и несогласованность | Разные протоколы, ad-hoc адаптеры, отсутствие стандарта | Определить стандартизованные интеграционные паттерны (API-first, SFTP, EDI), унифицировать адаптеры и тесты контрактов |
| 7 | Отсутствие RBAC/ABAC в аналитическом слое | Невозможность гибко разграничивать доступ к финансовым/персональным данным | Legacy-системы полагаются на приложение/PowerBuilder для авторизации | Встроить централизованную AuthZ (Keycloak + semantic layer enforcement) и интегрировать с каталогом |
| 8 | ML/AI потребляет чувствительные данные без контроля | Юридические и репутационные риски, "утечка" медицинских инсайтов | Нет ограничений, нет отдельных датапродуктов для ML с обезличиванием | Создать отдельные датапродукты для ML (обезличенные), процессы ревью модели и data-access approvals |
| 9 | Производительность при больших объёмах данных (сотни ТБ) | Высокие расходы, slow queries, растущие SLA-нарушения | DWH не подходит под scale-out; много трансформаций в базе | Переход на Lakehouse/отдельные движки (Trino/Dremio/Presto) для аналитики + partitioning, clustering, materialized views |
|10 | Отсутствие автоматизированных тестов для ETL/трансформаций | Риск регрессий при правках, сложности с поддержкой | Все трансформации в T-SQL/внутри DWH ручные | Ввести CI/CD для трансформаций, юнит/интеграционные тесты, data contracts |
